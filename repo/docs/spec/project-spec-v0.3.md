## 1. 개요 및 목적

냠냠취미는 숏폼 반응과 직접 고른 관심사로 취미를 추천하고, 상세 정보·주차별 TODO·장소·정보 피드·커뮤니티로 **첫 활동까지** 이어 주는 반응형 웹 서비스입니다.

### 1.1 배경

- 여가 불만족 사유 1·2위는 경제적 부담(48.7%)과 시간 부족(21.9%)이고, 향후 희망 여가활동으로 취미·자기개발(41.7%)이 꼽혔습니다(국가데이터처 사회조사).
- 유튜브 쇼츠 이용률은 2023년 58.1%에서 2025년 78.9%로 올랐습니다(2025 방송매체 이용행태조사). 익숙한 숏폼 형식으로 취미를 "맛보게" 하는 것이 출발점입니다.
- 프립·소모임·문토·문화포털은 예약·모임·문화정보 검색에 강하지만, **취미를 정하기 전의 관심사 탐색**과 **선택한 취미의 시작 준비**를 잇는 경험은 비어 있습니다.

### 1.2 주 사용자

| 사용자 | 상황 | 서비스가 주는 것 |
| --- | --- | --- |
| 취미를 찾는 사용자 | 무엇이 맞는지 모르고, 시간·비용이 부담됨 | 숏폼 반응 기반 추천, 시간·비용·난이도 비교, 첫 주 TODO |
| 이미 취미가 있는 사용자 | 행사·클래스·장소 정보를 흩어진 곳에서 찾음 | 취미별 정보 피드, 활동 장소, 게시판 |

### 1.3 목표

- **필수**: 숏폼 반응과 직접 선택(직접 선택은 \[P2·MVP 제외\])으로 취미를 추천하고, 관심 취미의 행사·클래스·입문 자료를 제공하는 웹 서비스를 2026-11-18 최종 발표 전까지 배포합니다. 사용자 테스트로 추천 적합성과 정보 유용성을 검증합니다.
- **심화**: 심리학 기반 취미 성향 검사를 설계·예비검증하고, 검사 결과를 추천에 결합했을 때 품질이 나아지는지 비교합니다.

### 1.4 핵심 사용 흐름

1. 숏폼을 보며 좋아요 / 별로예요 / 관련 없음으로 반응하고(마음에 드는 영상 보관은 \[P2·MVP 제외\]), 시청 시간도 함께 반영된다 (관심사 직접 선택은 \[P2·MVP 제외\]).
2. 관심 취미와 연관 취미를 추천받고, 추천 이유와 시간·비용·난이도를 비교한다.
3. 취미 상세에서 준비물·첫 활동을 확인하고 **관심 저장** 또는 **시작하기**를 누른다.
4. 시작한 취미의 주차별 TODO를 완료하며 진행률을 쌓는다.
5. 정보 피드·활동 장소·게시판으로 활동을 이어 간다.

### 1.6 이 명세서의 목적

계획서의 요구사항 29개를 **개발 단위(기능 ID · 화면 · 테이블 · API)** 로 쪼개고, 미정이던 정책에 기본안을 정해 구현 중 판단에 드는 시간을 줄입니다. 프론트엔드와 백엔드가 같은 용어·상태값·응답 형식을 쓰게 하는 것이 1차 목표입니다.

## 2. 용어 정의

코드·DB·API에서도 아래 영문 이름을 그대로 씁니다. 특히 **관심 취미(추천 유형)** 와 **관심 목록(저장 상태)** 은 다른 말입니다.

| 용어 | 코드명 | 정의 |
| --- | --- | --- |
| 취미 | `Hobby` | 서비스가 추천·관리하는 활동 단위. 관리자가 등록한다. 예: 클라이밍, 도예 |
| 취미 분류 | `Category` | 취미의 상위 묶음. 예: 운동·야외, 공예·만들기 |
| 태그 | `Tag` | 취미에 붙이는 유형 키워드. 예: #실내 #실외 #혼자 #함께 #활동적 #정적. 영상이 아니라 취미에 붙이며, 연관 취미 계산에 쓴다 |
| 숏폼 | `Short` | 취미 하나를 보여 주는 세로형 YouTube 영상(3분 이하). 관리자가 등록한 **신뢰 채널**에서 매일 모으고, 매주 한 번 노출 목록에 반영한 영상만 보여 준다 |
| 신뢰 채널 | `YoutubeChannel` | 관리자가 취미별로 등록한 YouTube 채널. 한 취미만 다루면 단일 채널(`SINGLE`), 여러 취미를 다루면 종합 채널(`MULTI`). 수집은 이 채널들에서만 한다 |
| 후보 영상 · 주간 반영 | `CANDIDATE` · `release` | 매일 수집해 필터를 통과한 영상은 후보로 쌓아 두고, 매주 정해진 시각에 한꺼번에 노출 목록(`ACTIVE`)으로 올린다 |
| 기계적 필터 | `MechanicalFilter` | 길이 3분 이하 · 퍼가기 허용 · 공개 영상 · 한국에서 재생 가능한 영상만 통과시키는 규칙 검사. GPT 판별 전에 한다 |
| 시청 비율 | `watchRatio` | 실제 재생한 초 ÷ 영상 길이(0\~1, 반복 재생은 1로 상한). 선호도 점수의 가중치로 쓴다 |
| 자동 숨김 | `AUTO_HIDDEN` | 관련 없음이 기준을 넘어 모든 사용자에게서 내린 영상. 관리자가 복구하거나 영구 제외한다(관리자 화면은 \[P3\], 그 전에는 DB 직접 수정) |
| 탐색 세션 | `ExplorationSession` | 숏폼 탐색 1회. 세션당 노출 수 N(설정값 `exploration.session-size`, 기본안 12)까지 보여 주며 진행률을 `n / N`처럼 표시한다 |
| 반응 | `Reaction` | 숏폼에 남긴 **좋아요(`LIKE`)** · **별로예요(`DISLIKE`)** · **관련 없음(`IRRELEVANT`)** 중 하나. 관련 없음은 취미와 상관없는 영상(밈·광고 등)이라는 표시로, 점수에서 빼고 다시 보여 주지 않는다. 넘기기는 반응이 아니지만 시청 시간은 남긴다 |
| 보관 | `ShortSave` | 플레이어의 보관 버튼으로 숏폼을 보관함에 담은 것. 반응(점수)과 별개이며 회원만 쓸 수 있다 \[P2·MVP 제외\] |
| 관심사 점수 | `InterestScore` | 반응·시청 비율(·직접 선택 \[P2\])으로 계산한 취미·태그별 선호 점수. 화면에는 % 막대로 보인다 |
| 이용 상황 | `UserCondition` | 활동 가능 시간(시간/주), 예산(원/월), 실내·실외, 혼자·함께 선호. 미입력 항목은 조건으로 쓰지 않는다 |
| 숙련도 | `SkillLevel` | 취미별 사용자 수준. `BEGINNER`(입문) · `NOVICE`(초급) · `INTERMEDIATE`(중급) |
| 관심 취미 (추천 유형) | `INTEREST` | 반응·선택에서 **직접** 높은 점수를 받은 취미 |
| 연관 취미 (추천 유형) | `RELATED` | 관심 취미와 태그·활동 특성이 비슷한, 아직 반응하지 않은 취미 |
| 탐색용 제안 | `isExploratory` | 관심사 정보가 부족할 때 보여 주는 추천. 화면에 배지로 구분한다 |
| 내 취미 | `UserHobby` | 사용자와 취미의 관계. 상태는 관심(`SAVED`) · 진행 중(`IN_PROGRESS`) · 일시중지(`PAUSED`) · 완료(`COMPLETED`) · 그만둠(`STOPPED`). `PAUSED`·`COMPLETED`·`STOPPED`는 취미 상태 변경(FR-MY-03, \[P2·MVP 제외\]) 도입 시 쓴다 |
| 관심 목록 | `SAVED` | "관심 저장"을 누른 취미 모음. 아직 시작하지 않은 상태 |

**비회원 정책 (MVP)** MVP에서 숏폼 탐색·추천은 로그인 후에만 쓴다. 비회원은 취미 검색·상세, 장소·정보 피드, 게시판 열람, 공지 조회처럼 공개 조회만 할 수 있다. 비회원이 숏폼 탐색·추천이나 회원 전용 버튼을 누르면 로그인 모달을 띄우고, 로그인 후 원래 화면으로 돌아온다(`redirect` 파라미터). 홈·숏폼 진입 시 로그인 요구 흐름은 11.1 확인 필요 사항에서 정리한다.

**비회원 체험 정책 \[기본안\] (Req.2) · \[P2·MVP 제외\]** — 아래는 비회원 체험 도입 시 규칙으로 남긴다.

- 비회원도 숏폼 탐색과 추천 결과 조회까지 할 수 있다. 첫 요청 때 서버가 `guestKey`(UUID)를 HttpOnly 쿠키로 발급하고, 반응은 이 키로 서버에 저장한다(보관 7일).
- 같은 브라우저에서 가입·로그인하면 탐색 세션과 반응을 회원 계정으로 **1회 이관**한다. 회원에게 같은 영상 반응이 이미 있으면 회원 기록을 남긴다.
- 비회원 화면 상단에 "로그인하지 않으면 7일 뒤 탐색 기록이 사라져요"를 항상 보여 준다.
- 비회원이 회원 전용 버튼(관심 저장, 시작하기 등)을 누르면 로그인 모달을 띄우고, 로그인 후 원래 화면으로 돌아온다(`redirect` 파라미터).

### 4.1 회원·인증 (AUTH)

**FR-AUTH-01 이메일 회원가입** · P0 · SCR-01-2

- **What** 이메일·비밀번호·닉네임으로 가입한다. 이메일 인증을 마쳐야 회원 기능을 쓸 수 있다.
- **How** ① 이메일·닉네임 입력 시 중복 확인 API 호출(입력 후 500ms 디바운스) ② 가입 요청 → 계정 `PENDING` 생성, 인증 메일 발송 ③ 메일 링크 클릭 → `ACTIVE` 전환 → 자동 로그인 후 01-5(이용 상황 설정, \[P1\]. 구현 전에는 00-2 홈)로 이동.
- **규칙** 이메일 최대 100자 · 비밀번호 8\~20자, 영문·숫자·특수문자 중 2종 이상 · 닉네임 2\~12자(한글·영문·숫자), 중복 불가 · 이용약관·개인정보 수집 동의 필수 · 인증 링크 24시간 유효·1회용 · 재발송은 60초에 1회.
- **예외** 가입된 이메일 → `409 AUTH_EMAIL_DUPLICATED` · 만료·사용된 링크 → "인증 메일 다시 보내기" 화면 · 소셜로 가입한 이메일과 같으면 "Google로 가입된 이메일이에요" 안내 \[P1, 소셜 로그인 도입 시\].

**FR-AUTH-02 로그인·로그아웃** · P0 · SCR-01-1

- **What** 이메일·비밀번호로 로그인하고, 로그아웃하면 인증 상태가 해제된다.
- **How** 성공 시 Access Token(30분)은 응답 본문, Refresh Token(14일)은 HttpOnly·Secure 쿠키로 받는다. Access가 만료되면 프론트가 `/auth/refresh`로 재발급한 뒤 원 요청을 다시 보낸다. 로그아웃은 서버에서 Refresh Token을 폐기하고 쿠키를 지운다.
- **규칙** 5회 연속 실패 시 5분 잠금 · 실패 문구는 "이메일 또는 비밀번호가 올바르지 않아요"로 통일(계정 존재 여부 비노출) · `PENDING` 계정은 인증 메일 재발송 안내.

**FR-AUTH-03 소셜 로그인** · P1 · SCR-01-1, 01-2

- **What** Google OAuth 2.0으로 가입·로그인한다(Kakao·Naver는 하지 않음).
- **How** Spring Security OAuth2 Client(Authorization Code). 콜백 후 서버가 토큰을 발급하고 프론트 `/oauth/callback`으로 리다이렉트한다. 최초 로그인이면 닉네임 확인(제공자 닉네임 기본값) 후 01-5(\[P1\])로 이동한다.
- **규칙 \[기본안\]** 계정 식별은 `(provider, providerUserId)`. 같은 이메일의 일반 계정이 있어도 **자동 연동하지 않고** "이메일로 가입된 계정이에요"를 안내한다(계정 탈취 방지). 소셜 계정은 이메일 인증을 생략한다.

**FR-AUTH-04 비밀번호 재설정** · P0 · SCR-01-3, 01-4

- **How** 이메일 입력 → 가입 여부와 관계없이 "메일을 보냈어요"로 동일하게 응답 → 재설정 링크(30분, 1회용) → 새 비밀번호 입력 → 기존 Refresh Token 전부 폐기 → 로그인 화면.
- **규칙** 새 비밀번호는 FR-AUTH-01 규칙을 따른다 · 소셜 전용 계정에는 "Google 로그인을 이용해 주세요" 메일을 보낸다(\[P1\] 소셜 로그인 도입 시).

**FR-AUTH-05 비회원 체험** · P2(MVP 제외) · SCR-00-1, 03-1

- MVP에서는 구현하지 않는다(숏폼 탐색·추천은 로그인 후에만). 아래는 도입 시 규칙으로 남긴다.
- 3장 "비회원 체험 정책"을 따른다. 로그인·가입 성공 직후 프론트가 `POST /explorations/merge`를 호출하고, 서버는 쿠키의 `guestKey`로 기록을 찾아 이관한 뒤 쿠키를 지운다.

**FR-AUTH-06 회원 탈퇴** · P0 · SCR-02-2 · 계획서에 없는 추가 제안(개인정보 처리에 필요)

- 비밀번호(소셜은 재로그인) 확인 후 탈퇴한다(P0). \[P1\] 이메일·닉네임은 즉시 익명화하고, 게시글·댓글은 "탈퇴한 사용자"로 표시해 남긴다. 같은 이메일로 바로 재가입할 수 있다. 익명화 전 단계에서 탈퇴 시 개인정보를 어떻게 처리할지(삭제·익명화)는 11.1 확인 필요 사항.

### 4.2 프로필·마이페이지 (USER)

**FR-USER-01 이용 상황 설정** · P1 · SCR-01-5

- **What** 가입 직후 관심 취미·숙련도, 활동 가능 시간, 예산, 실내·실외, 혼자·함께, 선호 지역을 입력한다. 모든 항목은 선택이며 "건너뛰기"할 수 있다.
- **입력 단위** 활동 가능 시간 = 시간/주(0\~40, 정수) · 예산 = 원/월(0\~1,000,000, 1만 원 단위) · 실내·실외 = `INDOOR` / `OUTDOOR` / `ANY` · 혼자·함께 = `ALONE` / `TOGETHER` / `ANY` · 관심 취미 최대 5개, 취미별 숙련도(기본 `BEGINNER`).
- **규칙** 미입력 항목은 `null`로 저장하고 추천·검색 조건에 쓰지 않는다. 입력한 관심 취미는 "관심 목록(`SAVED`)"으로도 저장된다.
- **완료 후** "저장하고 숏폼 탐색 시작" → 03-1, "건너뛰기" → 00-2(홈).

**FR-USER-02 프로필 수정** · P1 · SCR-02-2

- 관심 취미·숙련도, 이용 상황, 선호 지역을 수정한다(P1). \[P2·MVP 제외\] 닉네임, 프로필 이미지(선택, JPG·PNG 2MB 이하) 수정. 닉네임은 변경 시 중복을 확인한다.
- 저장해도 이미 만든 추천 결과는 바뀌지 않고, "다시 추천" 때 반영된다.

**FR-USER-03 비밀번호 변경** · P1 · SCR-02-3

- 현재 비밀번호 확인 → 새 비밀번호(규칙 동일, 현재와 같으면 거부). 변경 시 다른 기기의 Refresh Token을 폐기한다. 소셜 계정에는 메뉴를 숨긴다.

**FR-USER-04 마이페이지** · P0 · SCR-02-1

- 요약 카드 4개: 관심 취미 수 · 진행 중 취미 수 · 보관한 숏폼 수 · 내가 쓴 글 수.
- 탭: 진행 중 · 관심 취미 · 보관한 숏폼 · 내가 쓴 글 · 이용 상황. 진행 중 취미는 진행률 막대와 "이어하기"(→ 06-2)를 보여 준다.
- "보관한 숏폼" 카드·탭은 CSV상 P0이지만 숏폼 보관 기능(FR-SHORT-06)이 \[P2·MVP 제외\]라 **보관 기능 도입 전에는 숨긴다**(11.1 확인 필요 사항). 이용 상황 탭은 FR-USER-01·02(\[P1\])와 함께 만든다.
- 활동 인증·챌린지(P2)를 도입하면 참여 기록 탭을 추가한다.

### 4.3 숏폼 탐색 (SHORT)

숏폼은 **매일 모으고 → 매주 반영하고 → 실시간으로 보여 주고 → 반응으로 다시 거르는** 고리로 돕니다. 사전 준비(취미 20\~30개, 취미별 유형 태그, 신뢰 채널 등록)는 개발 초기에 한 번 수작업으로 하며, 관리자 화면(취미 콘텐츠는 \[P2\], 신뢰 채널 등록·승인은 \[P3\])이 없는 동안에는 시드 SQL(또는 DB 직접 수정)로 넣습니다.

> **도식: 숏폼 파이프라인 · 수집 → 반영 → 피드 → 걸러 내기 4단계** — Markdown에서는 그림이 빠집니다. [PDF 판](project-spec-v0.3.pdf) 12쪽을 보세요.

점선은 선호도 점수가 다음 피드의 70%(선호 취미)를 정하는 고리입니다(선호 70%·탐색 30%는 \[P1\], P0 단계는 무작위). GPT가 못 걸러 노출된 영상은 ④의 관련 없음 누적으로 내려갑니다.

**FR-SHORT-01 숏폼 재생** · P0 · SCR-03-1, 03-2

- **What** 노출 중(`ACTIVE`)인 영상 가운데 서버가 고른 1개를 세로 플레이어로 재생한다. 영상 확보는 FR-SHORT-07, 순서는 FR-SHORT-03.
- **How** YouTube IFrame Player API. 자동 재생은 브라우저 정책상 **음소거로 시작**하고 반복 재생한다. 다음 영상은 미리 불러와(`cueVideoById`) 전환을 1초 안에 끝낸다.
- **조작** 반응 버튼은 플레이어 오른쪽 세로 줄에 좋아요 · 별로예요 · 보관(\[P2·MVP 제외\]) · 다음(52px 원형, 아이콘 + 글자) 순서로 두고, 관련 없음은 그 아래 작은 텍스트 버튼으로 둔다. 재생/정지 · 음소거는 영상 오른쪽 위. 같은 반응 버튼을 다시 누르면 취소된다. 좋아요 · 별로예요 · 관련 없음을 누르면 0.3초 안에 다음 영상으로 넘어가고, 누른 버튼은 그동안 채움색(좋아요 = 피치)을 유지한다. \[P2\] 보관은 넘기지 않는다(FR-SHORT-06).
- **재생 실패** `onError`(코드 2·5·100·101·150) 또는 10초 동안 재생이 안 되면 "영상을 불러올 수 없어요"를 보여 주고 **2초 뒤 자동으로 다음 영상**으로 넘어간다(03-2, 플레이어 자리 안에 캐릭터 P4 + \[다음 영상 보기\]). 실패는 서버에 보고하고, 서로 다른 사용자 3명 이상에게 실패한 영상은 `UNAVAILABLE`로 바꿔 노출에서 뻔다.
- **개발용 데이터** 수집 배치(FR-SHORT-07)가 준비되기 전에는 시드 SQL로 넣은 `ACTIVE` 영상으로 개발·테스트한다.

**FR-SHORT-02 반응·시청 기록** · P0 · SCR-03-1

- 사용자 × 영상당 반응은 1개: `LIKE`(좋아요) · `DISLIKE`(별로예요) · `IRRELEVANT`(관련 없음: 취미와 상관없는 영상, 제목만 그럴듯한 밈·광고). 다른 반응을 누르면 바꾸고, 같은 반응을 다시 누르면 취소한다.
- `LIKE`·`DISLIKE`와 시청 비율은 관심사 점수에 쓴다(FR-RECO-01). `IRRELEVANT` 영상은 ① 그 사용자의 점수 계산에서 빼고 ② 그 사용자에게 다시 보여 주지 않으며(재탐색 포함) ③ 영상의 관련 없음 수를 1 올린다(FR-SHORT-08).
- **시청 시간** 다음 영상으로 넘기거나 화면을 떠날 때 실제 재생한 초(`watchedSeconds`)를 보낸다. 플레이어 상태 이벤트와 `getCurrentTime()`으로 재고, 반복 재생해도 영상 길이를 넘지 않게 자른다. 시청 비율 = 재생 초 ÷ 영상 길이(0\~1). 반응 없이 넘긴 영상도 시청 비율은 남긴다.
- 프론트는 낙관적 업데이트(버튼 상태 즉시 변경, 실패 시 되돌리고 토스트)를 쓴다.

**FR-SHORT-03 다음 영상 선택** · P0(일부 P1) · SCR-03-1, 03-4 · \[기본안\]

- 세션당 노출 수 N(설정값 `exploration.session-size`, 기본안 12)까지 보여 주며, 같은 세션에서 같은 영상은 다시 나오지 않는다. 화면 문구에 고정 숫자를 쓰지 않는다.
- **P0 단계 구현** `ACTIVE` 영상 중 본 영상·관련 없음·숨김 영상을 뺀 뒤 무작위로 고른다. 아래 첫 진입 분산과 선호 70%·탐색 30%는 P1 개선이다.
- \[P1\] **첫 진입**(관심사 점수가 아직 없을 때) 취미를 무작위로 골고루 섞는다. 1\~4번째는 서로 다른 분류에서 1개씩 고른다.
- \[P1\] **이후** 약 70%는 선호 취미(관심사 점수 상위)의 영상, 약 30%는 아직 덜 본 취미의 영상(탐색)으로 채운다. 영상을 고를 때마다 난수로 정하며 비율은 설정값(`exploration.prefer-ratio: 0.7`)이다. 별로예요를 받은 취미의 영상은 그 세션에서 뺀다.
- **제외** 이 사용자가 이미 본 영상(초기화 이후, 이전 세션 포함. 초기화는 \[P2\]), 관련 없음을 누른 영상(초기화와 상관없이 계속), `ACTIVE`가 아닌 영상(후보·숨김·이용 불가)은 고르지 않는다. 후보가 모자라면 이미 본 영상 중 반응이 없던 것부터 다시 쓴다.
- 종료 조건: ① 주어진 N개를 모두 보면 자동 종료 ② \[탐색 끝내기\]로 언제든 직접 종료 ③ 남은 후보 영상이 없으면 종료. 종료되면 추천을 만들고(FR-RECO-01) 04-3으로 이동한다.
- \[P1\] 반응(LIKE)이 3개 미만인 채 종료하면 추천 결과에 "탐색용 제안"을 표시한다(FR-RECO-01 ⑤).
- 다음 영상은 **서버가 결정**한다(`GET /explorations/{id}/next`). 프론트는 순서 로직을 갖지 않는다.

**FR-SHORT-04 탐색 진행 현황** · P0 · SCR-03-1

- 왼쪽 열: 진행 `n / N`(숫자 + 진행 바, 본 영상 기준, N은 세션 노출 수 설정값), 안내 문구("영상을 다 보면 추천해 드려요"처럼 고정 숫자 없이), 지금까지 반응한 취미 태그(별로예요는 회색 태그), 관심 주제 카드, 관심사 직접 선택(Secondary 버튼, \[P2·MVP 제외\]), 탐색 끝내기(Text 버튼).
- 관심 주제 카드(왼쪽 열): 상위 3개를 % 막대로 보여 주고 반응할 때마다 갱신한다. % = 해당 주제 점수 ÷ 최고 점수 × 100.

**FR-SHORT-05 관심사 직접 선택** · P2(MVP 제외) · SCR-03-3, 03-4

- MVP에서는 구현하지 않는다(직접 선택·탐색 기록 초기화 모두 P2). 아래는 도입 시 규칙으로 남긴다. 온보딩(FR-USER-01)의 관심 취미 선택은 별개라 P1 유지.
- 영상을 보지 않고 분류별 취미 칩을 골라(최대 10개) 하단 고정 바의 \[추천 결과 보기\](0개면 비활성) → 추천 생성. 선택은 언제든 고칠 수 있다.
- "처음부터 다시 탐색" 시 확인 모달("탐색 기록을 초기화할까요? 지금까지의 반응은 추천에 쓰이지 않아요")을 띄운다.
- 초기화는 사용자의 `interest_reset_at`만 갱신한다. 이후 관심사 점수는 이 시각 이후 반응만 계산하고, 보관함은 그대로 둔다. 관련 없음 처리한 영상은 초기화 후에도 다시 보여 주지 않는다.

**FR-SHORT-06 숏폼 보관함** · P2(MVP 제외) · SCR-05-1

- MVP에서는 구현하지 않는다(플레이어의 보관 버튼 포함). 아래는 도입 시 규칙으로 남긴다.
- 플레이어의 **보관** 버튼으로 담은 영상을 최근 보관순(보관 시각 내림차순)으로 20개씩 보여 주고, 취미 칩으로 거른다. 보관은 반응(좋아요 · 별로예요)과 별개라 관심사 점수에 쓰지 않는다 \[기본안\]. 비회원이 보관을 누르면 로그인 모달을 띄운다(`short_saves`, `PUT/DELETE /shorts/{shortId}/save`).
- 카드(5열): 9:16 YouTube 썸네일(모서리 16), 제목, 취미 태그, 보관일, 보관 해제(Text 버튼). 카드를 누르면 모달로 재생한다. 비어 있으면 캐릭터 P2 + "마음에 드는 영상을 보관해 보세요" + 숏폼 탐색하기 버튼.
- 영상이 `UNAVAILABLE`이면 썸네일을 회색 처리하고 "이용 불가" 배지와 \[보관 해제\] 버튼만 보여 준다.

**FR-SHORT-07 숏폼 수집·반영 (배치)** · P0(일부 P1) · SCR-10-4(\[P3\]) · \[기본안: 반영 요일·시각\]

- **What** 관리자가 등록한 신뢰 채널의 새 영상을 매일 모아 걸러 두고(`CANDIDATE`), 매주 한 번 노출 목록(`ACTIVE`)에 반영한다.
- **사전 준비(수작업, 1회)** 취미 20\~30개 선정 → 취미마다 유형 태그 지정(영상이 아닌 취미에 부여) → 취미별 신뢰 채널 등록. 시드 SQL(또는 DB 직접 수정)로 넣고, 10-4 관리자 화면의 채널 등록·승인은 \[P3\]. 채널 후보는 아래 '채널 발굴'로 반자동으로 찾는다.
- **수집(매일 04:00, Spring `@Scheduled`)** ① `ACTIVE` 채널마다 업로드 재생목록을 `playlistItems.list`로 조회해 마지막 수집 이후 영상만 고른다 ② `videos.list`로 길이·상태·지역 제한을 50개씩 한 번에 확인한다 ③ 기계적 필터 ④ 취미 지정 ⑤ 저장(`CANDIDATE` 또는 `NEEDS_REVIEW`).
- **기계적 필터** 길이 180초 이하(`contentDetails.duration`) · `status.embeddable = true` · `status.privacyStatus = public` · `contentDetails.regionRestriction`이 한국(`KR`)을 막지 않음. 하나라도 어기면 `REJECTED`(사유 기록)로 남겨 다시 수집하지 않는다.
- **취미 지정** 단일 채널(`SINGLE`)은 채널의 취미를 그대로 쓴다. 종합 채널(`MULTI`)은 제목·태그에서 매핑표의 숏폼 키워드를 찾고, 그래도 못 정하면 GMS(GPT-4o)에 제목·설명·썸네일을 보내 `{hobbyId, confidence, isHobbyContent}`를 받는다. 신뢰도 0.7 미만이거나 취미 영상이 아니라고 답하면 `NEEDS_REVIEW`로 둔다. GPT 호출은 배치 안에서 순차로 하고, 실패하면 `NEEDS_REVIEW`. `NEEDS_REVIEW` 영상은 관리자가 승인하기 전까지 **노출하지 않는다**. 확실한 영상(`CANDIDATE`)은 관리자 없이 주간 반영으로 사용자에게 나가므로 관리자가 로그인해 있지 않아도 서비스가 돈다. 이 저장 구조는 P0 수집 배치에서 미리 만들어 두어 관리자 검토 화면(FR-ADM-07, \[P3\])을 언제든 붙일 수 있게 한다. 검토 화면에서 승인하면 `NEEDS_REVIEW` → `CANDIDATE` → 다음 주간 반영 때 `ACTIVE`, 거절하면 `REJECTED`이고, 화면이 생기기 전에는 노출하지 않은 채 둔다.
- **주간 반영(매주 목 06:00 \[기본안\])** 그 주에 쌓인 `CANDIDATE`만 한 번에 `ACTIVE`로 올린다(`released_at` 기록). 상태값만 바꾸므로 서비스를 멈추지 않는다. `NEEDS_REVIEW`는 반영 대상이 아니며, 관리자 승인(\[P3\])으로 `CANDIDATE`가 된 영상만 다음 반영에 들어간다. \[P2·MVP 제외\] 10-4의 "지금 반영" 수동 실행.
- \[P1\] **기존 영상 점검(매일 04:30)** `ACTIVE` 영상을 `videos.list`로 50개씩 다시 조회해 삭제·비공개·퍼가기 금지·지역 제한이 생긴 영상을 `UNAVAILABLE`로 내린다.
- **채널 발굴(매주 월 06:00)** 매핑표의 숏폼 키워드(예: `클라이밍 #shorts`, `뜨개질 초보`)로 `search.list`(`type=video`, `videoDuration=short`, `regionCode=KR`)를 부르고, 여러 번 나온 채널을 `youtube_channels`에 후보(`CANDIDATE`)로 저장한다. 승인해야 신뢰 채널(`ACTIVE`)이 되며, 승인 화면(10-4)은 \[P3\]이고 그 전에는 DB에서 직접 `ACTIVE`로 바꾼다(11.1 A4, 해결).
- **할당량** YouTube Data API 기본 할당량은 하루 10,000단위이고 `channels.list`·`playlistItems.list`·`videos.list`는 호출당 1단위다. `search.list`는 하루 100회 별도 한도가 있어 실시간 검색에는 쓰지 않는다([공식 문서](https://developers.google.com/youtube/v3/determine_quota_cost)). 채널 90개(취미 30개 × 3) 기준 하루 200단위 안팎이며, 사용량은 `batch_runs`에 남긴다. 할당량은 미국 태평양 시간 자정(한국 16\~17시)에 초기화된다.
- **실패** API 오류·할당량 초과가 난 채널은 `last_collected_at`을 갱신하지 않아 다음 날 이어서 수집한다.

**FR-SHORT-08 관련 없는 영상 자동 숨김** · P0(일부 P1) · SCR-03-1, 10-4(\[P3\]) · \[기본안: 숨김 기준\]

- **What** GPT가 못 걸른 영상(제목은 취미 관련처럼 보이지만 내용은 밈·광고 등)을 사용자 반응으로 걸러 낸다.

- \[P1\] 같은 채널에서 자동 숨김이 3건 이상 나오면 채널에 "점검 필요"를 표시한다(수집은 계속).
- \[P3\] 관리자는 10-4에서 자동 숨김 영상을 **복구**(`ACTIVE`, 카운트 초기화) 또는 **영구 제외**(`REJECTED`)한다. 그 전에는 DB에서 직접 바꾼다.

### 4.5 추천 (RECO)

**FR-RECO-01 추천 생성** · P0 · \[기본안\]

- **입력** 초기화 이후 반응(초기화는 \[P2\]), 직접 선택한 관심사(\[P2\]), 이용 상황(\[P1\]), "별로예요" 처리한 취미.
- **① 관심사 점수** 영상 점수 = 반응 점수(LIKE +3, DISLIKE −3, 반응 없음 0) + 시청 가중치(시청 비율 × 2 − 1, −1\~+1). 취미 점수 = 그 취미 영상 점수의 합(+ 직접 선택 +5는 \[P2·MVP 제외\]). 태그 점수 = 영상 점수 × 0.3을 그 영상 취미가 가진 태그마다 더한 값. 관련 없음(IRRELEVANT) 영상과 재생 실패 영상은 넣지 않는다. 예: 끝까지 보고 LIKE = +4, 3초 만에 넘김 = 약 −1.
- **② 관심 취미(`INTEREST`)** 취미 점수가 0보다 큰 상위 3개.
- **③ 연관 취미(`RELATED`)** 후보 점수 = 관심 취미와의 최대 유사도 × 0.7 + 정규화한 태그 점수 × 0.3. 유사도는 태그 벡터의 코사인 유사도로, Spring 일 배치(`@Scheduled`, 9.4)가 `hobby_similarity`에 미리 계산해 둔다. 상위 3개. 이미 관심 취미로 나온 것, 진행 중인 것, 별로예요 처리한 것은 뺀다.
- \[P1\] **④ 이용 상황** 걸러내지 않고 **정렬 가중치**로만 쓴다. 월 비용 최솟값이 예산을 넘거나 1회 시간 최솟값이 주간 가능 시간을 넘으면 ×0.8을 하고 카드에 "조건 확인 필요" 배지를 붙인다. 실내·실외, 혼자·함께가 맞으면 ×1.1.
- \[P1\] **⑤ 정보 부족** LIKE 3개 미만이면(직접 선택이 없다는 조건은 \[P2\] 도입 시 추가) 인기 취미(관심 저장 수) 중 서로 다른 분류 6개를 `isExploratory = true`로 돌려준다.
- 결과는 `recommendations` 스냅샷으로 저장해 다시 열어도 같은 결과를 보여 주고, 새 추천은 "다시 추천" 때만 만든다. 생성 API는 3초 안에 응답한다.
- 가중치(+3, ×0.8 등)는 설정값(`application.yml`)으로 빼서 사용자 테스트 후 조정한다.

**FR-RECO-02 추천 결과** · P0(일부 P1) · SCR-04-3

- **상단** "{닉네임}님을 위한 추천 취미" + \[P1\] 추천 기준 문구(예: "숏폼 12개 중 9개의 반응과 이용 상황(주 3시간 · 월 15만 원)을 바탕으로 추천했어요").
- **본문** 관심 취미 / 연관 취미 두 섹션. 카드 = 이미지, 이름, 추천 이유 1문장, 시간·비용·난이도 칩, 관심 저장 · 별로예요 · 자세히 보기.
- \[P1\] **추천 이유** GMS(GPT-4o)로 만든다(P0 단계에서는 템플릿 문구만 보여 준다). 입력은 반응 요약(취미별 LIKE 수, 상위 태그)과 취미 정보, 출력은 60자 이내 한국어 1문장. 추천 생성 직후 RabbitMQ로 비동기 생성·저장하며, 준비 전이거나 GMS가 실패하면 템플릿 문구("클라이밍 영상에 좋아요 3회")를 보여 준다.
- \[P1\] **탐색용 제안일 때** "아직 관심사를 파악하는 중이에요" 배너 + "숏폼 더 보기" 버튼("관심사 직접 선택" 버튼은 \[P2·MVP 제외\]).

**FR-RECO-03 추천 피드백** · P0 · SCR-04-3

- **관심 저장** FR-MY-01과 같다.
- **별로예요** 해당 취미를 `hobby_dislikes`에 넣고 카드를 흐리게 바꾼다. 토스트 "다음 추천에서 빼 드릴게요"에 5초 동안 "되돌리기". 이후 추천·연관 후보에서 빠지며, 마이페이지 이용 상황 탭(\[P1\])에서 해제할 수 있다.

- \[P2·MVP 제외\] `PAUSED`·`STOPPED` 상태에서는 변경 불가(`409 TODO_PLAN_NOT_ACTIVE`).

**FR-TODO-03 내 계획 수정** · P2(MVP 제외) · SCR-06-2 · \[기본안: 허용\]

### 4.8 장소 (PLACE)

**FR-PLACE-01 선호 지역 선택** · P1 · SCR-01-5, 02-2, 07-1

- 시·도 → 시·군·구 2단계 드롭다운(행정구역 코드). 사용자당 1개 지역을 저장한다.
- 현재 위치 권한·GPS는 쓰지 않는다. 미선택이면 장소 화면에서 지역 선택을 먼저 요청한다.

**FR-PLACE-02 활동 장소 추천** · P1 · SCR-07-1

- 선호 지역 + 취미(내 취미 칩 중 선택)에 맞는 장소를 왼쪽 목록 + 오른쪽 지도(카카오맵 JavaScript API)로 보여 준다. 목록을 고르면 마커가 강조되고, 마커를 고르면 목록이 스크롤된다.
- **장소 정보** 이름, 분류(공원 · 공공체육시설 · 공방·클래스 · 체육관), 주소, 운영 시간, 비용, 외부 링크, 출처, 갱신일.
- **데이터 출처** 공원: 공공데이터포털 전국도시공원정보표준데이터 · 공공체육시설: 공공데이터포털 공공체육시설 데이터 · 공방·클래스·체육관: 카카오 로컬 API 키워드 검색. 수집·병합 규칙은 FR-PLACE-03.
- **지역 범위 \[기본안\]** MVP는 서울특별시 데이터만 수집·제공한다. 시·도 목록에서 서울 외 지역은 "준비 중"으로 비활성화하고, 전국 확장은 고도화로 둔다.
- 운영 시간·비용이 비었거나 90일 넘게 갱신되지 않은 장소는 "정보 확인 필요" 배지를 붙인다. 지도 API가 실패하면 목록만 보여 준다.

**FR-PLACE-03 장소 수집·병합 (배치)** · P1 · SCR-07-1, 10-1(\[P2\]) · \[기본안: 병합 기준·주기\]

- **매핑표** 같은 취미도 출처마다 이름이 다르다(예: 클라이밍 → 카카오 "클라이밍장", 공공체육시설 "인공암벽장", 행사 "볼더링"). 취미마다 카카오 검색어 · 공공데이터 종목명 · 공원 시설 키워드를 `hobby_source_mappings`에 둔다. 처음에는 엑셀로 정리해 시드 SQL로 넣고, MVP에서는 시드 SQL·DB 직접 수정으로 고친다(10-1의 '데이터 매핑' 화면은 \[P2·MVP 제외\]).
- **수집 주기** 공원·공공체육시설은 거의 바뀌지 않으므로 매월 1일 03:30, 카카오 로컬(공방·클래스·체육관)은 매주 화 03:30.
- **카카오 검색** 서울 25개 구 × 취미별 카카오 검색어로 키워드 검색을 부른다. 카테고리명으로 음식점 같은 무관한 결과를 거른다.
- **좌표** 주소만 있는 공공데이터는 카카오 로컬 "주소로 좌표 변환"으로 위경도를 채운다. 변환에 실패하면 지도에서 빼고 목록에만 보여 준다.
- **중복 병합** 출처가 달라도 같은 장소면 하나로 합친다. 좌표 거리 50m 이내 **그리고** 이름 유사도 0.6 이상(공백·괄호·"점" 제거 후 비교)이면 같은 장소로 본다. 50m 이내라도 이름이 다르면 같은 건물의 다른 시설일 수 있어 따로 둔다. 대표 정보는 공공데이터 > 카카오 순으로 쓰고, 출처별 원본은 `place_sources`에 남긴다.
- **공개** 공공데이터 장소는 바로 `PUBLISHED`. 카카오 로컬로 새로 들어온 장소도 MVP에서는 카테고리 규칙을 통과하면 바로 `PUBLISHED`로 둔다. \[P2·MVP 제외\] `PENDING_REVIEW`로 두고 관리자가 확인하는 검토 단계(FR-ADM-06)는 P2 도입 시(11.1 확인 필요 사항).
- **쿼터** 카카오 로컬 키워드 검색·주소 변환은 각각 하루 100,000건 무료다([카카오 쿼터](https://developers.kakao.com/docs/latest/ko/getting-started/quota)). 서울 25개 구 × 취미 30개 × 3페이지 ≈ 주 2,250건으로 충분하다. 무료 쿼터는 개발자 계정당 처음 활성화한 앱에만 주므로 팀 공용 앱 키 하나를 쓴다.
- **멱등성** `(source, source_ref)` 유니크로 다시 돌려도 중복이 생기지 않고, 실행 결과는 `batch_runs`에 남긴다.

### 4.11 커뮤니티 (BOARD)

**FR-BOARD-01 게시판 목록** · P1 · SCR-08-1

- 왼쪽에 취미 게시판 목록(내 취미가 위), 위쪽에 유형 탭(전체/질문/정보/후기/활동 공유), 제목·내용 검색, 정렬(최신/좋아요), 페이지 번호(20개씩).

**FR-BOARD-02 게시글 작성** · P1 · SCR-08-3

- **입력** 취미(필수), 유형(필수), 제목 2\~50자, 본문 10\~5,000자(일반 텍스트 + 줄바꿈), 이미지 최대 5장(JPG·PNG·WEBP, 장당 5MB).
- 작성자 본인만 수정·삭제(`403 BOARD_FORBIDDEN`). 삭제는 soft delete로 목록에서 빠지고 상세는 `404`.
- 작성 중 이탈하면 확인 모달. 등록하면 상세로 이동한다.
- 서버는 HTML을 이스케이프해 저장하고, 프론트는 텍스트로만 렌더한다(`dangerouslySetInnerHTML` 금지).

**FR-BOARD-03 게시글 상세·댓글** · P1 · SCR-08-2

- 본문, 이미지, 좋아요·댓글 수, 링크 복사, 신고(\[P3\]), (본인) 수정·삭제.
- 댓글 1\~500자. 대댓글은 1단계만(대댓글의 답글도 부모 댓글 아래에 붙는다). 본인 댓글만 수정·삭제. 대댓글이 있는 댓글을 지우면 "삭제된 댓글입니다"로 남긴다.
- 조회수는 같은 회원 기준(비회원 체험 도입 시 guestKey 포함) 24시간에 1회 올린다.

**FR-BOARD-04 좋아요** · P1 · SCR-08-2

- 게시글·댓글에 회원당 대상별 1회, 다시 누르면 취소. UNIQUE `(user, targetType, targetId)`. 개수는 비정규화 컬럼(`like_count`)으로 관리한다.

**FR-BOARD-05 링크 공유** · P1 · SCR-04-4, 08-2 · \[기본안\]

- 취미 상세와 공개 게시글에 "링크 복사"(Clipboard API)만 둔다. SNS 공유는 P2.
- 숨김·삭제 글, 개인 TODO·활동 기록에는 공유 버튼이 없다.

### 4.14 관리자 (ADMIN)

관리자 화면은 `/admin` 아래 별도 레이아웃이며 `ADMIN`만 들어올 수 있다. 모든 관리자 조치는 처리자·시각을 남긴다.

**MVP 운영 방식** 관리자 화면은 대부분 \[P2·MVP 제외\]입니다. 취미 콘텐츠·분류·태그·TODO 원본·데이터 매핑표·신뢰 채널은 **시드 SQL(또는 DB 직접 수정)** 로 넣고, 정보 피드·카카오 장소는 검토 단계 없이 바로 `PUBLISHED`로 둡니다. 숏폼은 관리자 없이도 돌아갑니다: P0 수집 배치가 확실한 영상은 `CANDIDATE`, 불확실한 영상은 `NEEDS_REVIEW`로 저장하고, P0 주간 반영 배치가 `CANDIDATE`만 `ACTIVE`로 올리므로 관리자가 로그인해 있지 않아도 사용자에게 영상이 나갑니다. `NEEDS_REVIEW` 영상과 채널 발굴로 저장된 후보 채널(`CANDIDATE`)은 관리자가 승인할 때까지 노출·수집하지 않습니다. 숏폼 검수(신뢰 채널 등록·승인, 후보 영상 검토·승인, 자동 숨김 복구·제외, FR-ADM-07)는 팀 결정(10/21)으로 \[P3\]이며, 저장 구조를 P0에서 미리 만들어 두어 언제든 화면을 붙일 수 있습니다(그 전에는 DB에서 직접 승인). `/admin` 레이아웃·라우트는 P3 기능(신고 검토 · 문의 답변 · 공지 관리 · 숏폼 검수)용으로 필요하므로 \[P3\]입니다.

**FR-ADM-01 취미 콘텐츠 관리** · P2(MVP 제외, 시드 SQL로 대체) · SCR-10-1

- 취미 목록(분류·상태 필터, 검색) → 등록·수정: 분류, 이름, 태그, 요약, 소개, 활동 환경, 준비물, 비용 범위, 시간 범위, 난이도, 첫 활동, 유의 사항, 대표 이미지.
- 상태는 `DRAFT` → `PUBLISHED` ↔ `HIDDEN`. 필수 항목(이름·분류·요약·비용·시간·난이도·대표 이미지·태그 1개 이상)이 빠지면 공개 버튼을 막고 빠진 항목을 표시한다.
- 분류·태그 추가·이름 변경·정렬. "태그 추천" 버튼은 소개 문구를 GMS에 보내 후보를 받고, 관리자가 골라 저장한다.
- 숏폼 신뢰 채널·후보 영상·주간 반영은 FR-ADM-07(10-4)에서 관리한다. 취미 등록 때 유형 태그(실내·실외, 혼자·함께, 활동적·정적 등)를 붙인다.

**FR-ADM-02 TODO 원본 관리** · P2(MVP 제외, 시드 SQL로 대체) · SCR-10-1

- 취미 × 숙련도별 원본: 계획명, 총 주차, 주차별 활동(제목, 설명, 예상 소요 시간(분), 준비물, 완료 기준, 순서). 활동마다 제목·예상 시간·완료 기준은 필수.
- 저장할 때마다 버전이 1 올라가며, 진행 중인 사용자 계획에는 반영하지 않는다(FR-TODO-03).
- 공개 원본이 1개 이상 있어야 그 취미의 "시작하기"가 열린다.

**FR-ADM-03 신고 검토** · P3 · SCR-10-2

- 신고 목록: 대상 유형·상태 필터, 대상별 묶음(신고 수 = 고유 신고자 수), 오래된 순.
- 상세: 대상 원문, 신고 사유 목록, 작성자의 과거 조치 횟수.
- 조치: 숨김 / 유지(기각) / 숨김 해제. 조치 사유 필수. **\[기본안\]** 계정 정지 같은 사용자 제재는 MVP에서 빼고 콘텐츠 숨김만 한다. 이의 제기는 고객 문의로 받는다.

**FR-ADM-04 문의 답변** · P3 · SCR-10-3

- 상태 필터 → 답변 작성·수정. 답변을 저장하면 `ANSWERED`로 바뀐다. \[P2·MVP 제외\] 작성자에게 알림을 보낸다(알림 도입 시).

**FR-ADM-05 공지 관리** · P3 · SCR-10-3

- 작성(제목·분류·본문·상단 고정), 임시 저장 / 게시, 수정, 삭제. 게시할 때 "전체 알림 보내기"를 고를 수 있다(CSV상 P3이지만 알림 기능이 \[P2\]라 11.1 확인 필요 사항).

**FR-ADM-06 정보 피드·장소 관리** · P2(MVP 제외) · SCR-10-1

- 정보 피드와 장소를 직접 등록·수정·비공개하고, 배치로 들어온 `PENDING_REVIEW` 항목(카카오 로컬 장소, 수집 피드)을 확인해 공개한다.
- **데이터 매핑** 취미 편집 화면(10-1)의 '데이터 매핑' 영역에서 취미별 카카오 검색어 · 공공데이터 종목명 · 행사 검색어 · 숏폼 키워드를 추가·삭제한다. 바꾼 매핑은 다음 수집부터 쓴다.

**FR-ADM-07 숏폼 채널·영상 관리** · P3(일부 P2) · SCR-10-4

- 팀 결정(10/21): 숏폼 검수(신뢰 채널 등록·승인, 후보 영상 검토·승인, 자동 숨김 복구·제외)는 \[P3\], 주간 반영 화면의 "지금 반영"과 수집 현황은 \[P2·MVP 제외\]이다. 저장 구조는 P0 배치(FR-SHORT-07)에서 미리 만든다: 확실한 영상은 `CANDIDATE`로 저장돼 주간 반영으로 자동 노출되고, 불확실한 영상은 `NEEDS_REVIEW`로 남아 승인 전까지 노출하지 않는다. 그래서 관리자가 없어도 사용자는 영상을 받는다. 검토 화면이 생기기 전에는 채널 승인·자동 숨김 복구를 DB에서 직접 한다.

- \[P3\] **신뢰 채널** 취미별 채널 목록(상태, "점검 필요" 표시), 등록(채널 URL 또는 ID → `channels.list`로 이름·업로드 재생목록 확인), 유형(단일·종합)과 담당 취미 지정, 수집 중지. 채널 발굴로 올라온 후보를 승인·거절한다.
- \[P3\] **후보 영상** 이번 주 `CANDIDATE`·`NEEDS_REVIEW` 목록: 썸네일, 제목, 채널, 길이, 지정된 취미와 방법(채널 상속 · 키워드 · GPT + 신뢰도). 취미 변경, 승인(`NEEDS_REVIEW` → `CANDIDATE`, 다음 주간 반영 때 `ACTIVE`), 제외(`REJECTED`)를 한다.
- \[P2·MVP 제외\] **주간 반영** 다음 반영 예정 시각, 반영 대상 수(취미별), 지난 반영 이력. "지금 반영"은 확인 모달 뒤 실행하며, 실행 중에는 다시 누를 수 없다(`409 ADMIN_RELEASE_IN_PROGRESS`).
- \[P3\] **자동 숨김·이용 불가** 관련 없음 수·비율, 재생 실패 수와 함께 보여 주고 복구 또는 영구 제외한다.
- \[P2·MVP 제외\] **수집 현황** 최근 배치 실행 결과(수집·통과·제외 수, YouTube 할당량 사용량, 실패한 채널)를 `batch_runs`에서 보여 준다.

### 4.15 서비스 피드백 (FEEDBACK) · P2(MVP 제외)

기능 요구사항 CSV에서 빠져 **P2(MVP 제외)** 로 두고, 아래 본문은 고도화 후보로 남깁니다. `feedback.analyze` 큐와 Mattermost 피드백 알림도 P2입니다.

답변이 필요한 1:1 문의(FR-CS-01)와 달리, 피드백은 답변 없이 **빨리 받고 자동으로 분류해 운영팀에 전달**하는 흐름입니다. 제출 응답과 AI 분석을 분리해 사용자는 기다리지 않습니다.

**FR-FB-01 서비스 피드백 제출** · P2(MVP 제외) · 모든 화면 우하단 "피드백 보내기" 모달

- **What** 회원이 쓰는 중 겪은 오류·불편·의견을 바로 보낸다.
- **입력** 유형(선택: 오류 · 추천 · 콘텐츠 · 제안 · 기타), 내용 10\~1,000자. 현재 화면 경로, 브라우저·OS, (추천 화면이면) 추천 ID를 자동으로 붙인다.
- **서버 처리 순서** ① 인증 확인 ② 요청량 제한(10분에 3회, 5.1) ③ 입력값 검증 ④ DB 저장(`RECEIVED`) ⑤ 즉시 `202 Accepted` 응답. 프론트는 "의견 고마워요" 토스트를 띄우고 모달을 닫는다.
- **규칙** AI 분석은 응답 뒤에 비동기로 한다(응답 시간에 포함 안 함). 이메일 등 개인정보는 외부 알림에 넣지 않는다.

**FR-FB-02 피드백 AI 분석·Mattermost 알림** · P2(MVP 제외) · SCR-10-3(피드백 탭)

- **분석** 저장 직후 RabbitMQ `feedback.analyze` 큐에 피드백 ID를 넣는다. 컨슈머가 GMS로 우선순위, 유형, 1\~2문장 요약을 만들어 저장한다(`ANALYZED`).
- **우선순위 기준** `URGENT` 로그인·가입 불가, 데이터 유실, 개인정보 노출, 서비스 전체 오류 · `HIGH` 주요 기능(탐색·추천·TODO) 오류 · `NORMAL` 불편·개선 요청 · `LOW` 단순 의견.
- **알림** `URGENT`는 즉시 Mattermost 운영 채널(Incoming Webhook)에 요약과 관리자 화면 링크를 보낸다. 나머지는 매일 18:00에 지난 24시간분을 우선순위별 개수 + 요약 목록으로 1건 보낸다.
- **실패 처리** GMS·Mattermost 호출이 실패하면 1분 → 5분 → 15분 간격으로 최대 3회 자동 재시도한다(RabbitMQ 지연 큐 + DLQ). 끝내 실패하면 `ANALYSIS_FAILED`로 두고, 정기 요약에 "미분석" 원문으로 넣으며 관리자가 재분석할 수 있다.
- **멱등성** 같은 메시지를 두 번 받아도 상태를 먼저 확인해 한 번만 처리하고, 알림은 `notified_at`이 비어 있을 때만 보낸다.
- **관리자** 10-3의 피드백 탭에서 우선순위·상태 필터, 요약·원문 보기, 재분석.

### 5.1 요청량 제한 (Redis Rate Limit) · 고도화(P3 수준, 여유 시)

기능 요구사항 CSV에 없는 비기능 항목이라 내용은 그대로 두고, P0·P1을 마친 뒤 여유가 있을 때(P3 수준) 적용합니다.

과도한 요청은 **토큰 버킷**으로 막습니다. 요청마다 토큰 1개를 쓰고, 토큰은 정해진 속도로 자동 충전되며, 버킷이 비면 거절합니다.

- **저장소** 버킷 상태는 Redis에 둔다(Bucket4j + Lettuce, 또는 Lua 스크립트로 원자적 차감). 서버가 여러 대여도 한도가 같다.
- **기준 키** 로그인 사용자는 `rl:{정책}:u:{userId}`, 비회원·로그인 전 요청은 `rl:{정책}:ip:{IP}`. IP는 Nginx가 넣는 `X-Forwarded-For`의 첫 값.
- **초과 시** `429 COMMON_RATE_LIMITED` + `Retry-After: {초}` 헤더 + 본문 `retryAfterSeconds`. 프론트는 "잠시 후 다시 시도해 주세요 (n초)"를 보여 주고 자동 재시도하지 않는다. 성공 응답에도 `X-RateLimit-Remaining`을 넣는다.
- **Redis 장애 시** 요청을 허용(fail-open)하고 경고 로그를 남긴다. 로그인 잠금은 DB 기반이라 영향이 없다.
- **설정** 정책별 허용량은 `application.yml`의 `rate-limit.policies`에 둔다. 아래는 초깃값이며 통합 테스트 때 조정한다.

| 정책 | 대상 API | 기준 | 버킷 크기 | 충전 속도 |
| --- | --- | --- | --- | --- |
| `default-user` | 아래에 없는 모든 API | 사용자 | 100 | 100개/분 |
| `default-guest` | 아래에 없는 모든 API(비회원) | IP | 60 | 60개/분 |

### 6.2 공통 레이아웃·상태 규칙

- **레이아웃**: 콘텐츠 최대 폭 1200px 가운데 정렬, 12열 · 간격 24 · 좌우 여백 24(모바일 16). GNB 아래 40 · 섹션 사이 48 · 하단 80. 모든 화면은 A 가운데 카드(폭 440, 01) · B 카드 그리드(4열, 숏폼 카드 5열) · C 사이드 + 본문(06-2, 08-1) · D 목록 + 상세(5:7, 07-1, 09-2·3) 중 하나이고, 03 숏폼만 예외(왼쪽 진행 정보 · 가운데 9:16 플레이어 · 오른쪽 반응 버튼)입니다. 관리자 화면은 좌우 여백 40으로 넓게 씁니다.
- **GNB**: 비회원은 메뉴 5개 + 로그인·회원가입, 회원은 메뉴 5개 + 알림(\[P2·MVP 제외\])·마이페이지·로그아웃, 관리자는 관리 메뉴 4개(취미 콘텐츠·TODO(\[P2\]) · 숏폼 채널·영상(\[P3\]) · 신고 검토(\[P3\]) · 문의·공지(\[P3\])·피드백(\[P2\])) + 서비스 화면으로·로그아웃입니다(관리자 레이아웃은 \[P3\]). 메뉴 5개는 숏폼 탐색 · 취미 찾기 · 장소·정보 · 커뮤니티 · 공지입니다. 높이 64 · 흰 바탕 · 아래 1px 선 · 로고 36px이고, 현재 메뉴는 잉크 글자 + 아래 2px primary 선, 알림 배지는 Spark Orange 바탕 + 잉크 숫자(99+까지)입니다.
- **버튼 위계**: 한 화면에 주 버튼(Primary)은 하나입니다. 보조는 Secondary, 더 보기 · 재설정 · 신고는 Text, 신고 확정 · 탈퇴 · 삭제 확정은 모달 안의 Danger만 씁니다. 순서는 \[보조\]\[주\]로 주 버튼이 오른쪽이고, 크기는 L52(페이지 하단 확정) · M44(기본) · S36(카드 안)입니다.
- **태그 색**: 관심 · 진행 중 = Teal, 연관 = Mint, 완료 = Success(체크), 일시중지 · 분류 = Gray, 새 소식 · 주의 = Peach, 관리자 · 개발 메모 = Dark, 썸네일 위 = White. 태그는 누를 수 없는 24px 라벨이고, 상태는 색 + 글자로 함께 알립니다.
- **상태 네 가지(C-2)**: 로딩은 실제 카드 모양 스켈레톤(응답이 300ms를 넘을 때만, 1초 넘는 전체 로딩만 캐릭터 P6)입니다. 비어 있음은 캐릭터 + 제목(display/m) + 설명 한 줄 + 행동 1\~2개, 오류는 문제가 난 자리 안에서 무엇이 안 됐는지 + 할 수 있는 행동 + `X-Request-Id` 앞 8자리, 완료는 하단 스낵바(큰 완료만 캐릭터 P5)입니다. 429는 `retryAfterSeconds`로 "n초 후 다시 시도해 주세요"를 띄우고 자동 재시도하지 않습니다.
- **로그인 필요**: 비회원이 회원 전용 행동(숏폼 탐색·추천, 관심 저장, 시작하기, 글쓰기 등)을 누르면 로그인 모달을 띄웁니다. 로그인 후 `redirect`로 원래 화면에 돌아옵니다. 비회원 탐색 기록 이관(FR-AUTH-05)은 \[P2·MVP 제외\]입니다.
- **모달 · 스낵바**: 모달은 너비 400(확인) · 480(입력 있음), 모서리 24, 딘 rgba(27,42,49,.48), 버튼은 오른쪽 정렬입니다. ESC · 바깥 클릭으로 닫고, 작성 중이면 확인 모달을 띄웁니다. 스낵바는 화면 아래 가운데, 잉크 바탕 · 흰 글자 · 민트 행동 링크로 4초 유지합니다(되돌리기가 있으면 5초).
- **피드백 버튼** \[P2·MVP 제외\]: 회원 화면 오른쪽 아래에 항상 떠 있고, 누르면 C-1 모달이 열립니다.
- **캐릭터**: 안내자 역할이라 처음 · 비어 있을 때 · 실패 · 완료에만, 한 화면에 한 번 나옵니다. 크기는 빈 상태 160 · 히어로 200\~240 · 모달 96이고 48 미만에는 쓰지 않습니다. 옆에는 반드시 제목 + 다음 행동을 둡니다. 원본은 P1뿐이며 P2\~P7은 제작 전까지 Figma에 점선 자리표시로 두었습니다(11장).

### 6.6 문구 · 용어 규칙

화면 문구는 취미를 먼저 해 본 다정한 친구처럼 해요체로 짧게 쓰고, 사용자를 탓하지 않습니다(컨셉북 19장). 서버가 돌려주는 오류 `message`(8.4)도 같은 규칙을 따릅니다.

| 화면 용어 | 뜻 | 쓰지 않는 말 |
| --- | --- | --- |
| 관심 취미 · 연관 취미 | 직접 고르거나 반응한 취미 · 그와 비슷한 취미 | — |
| 관심 저장 | 취미를 관심 목록에 담기 | 찜, 북마크 |
| 보관 · 보관함 | 숏폼을 담을 때만 | 찜, 북마크 |
| 좋아요 · 별로예요 | 숏폼 반응, 추천 카드에서 빼기 | 마음에 듦, 별로임, 싫어요 |
| 시작하기 | 취미를 내 취미로 옮기기 | — |
| 주차별 TODO · 건너뛰기 | 주차 계획 · 상태 표시는 "건너뜀" | 할 일, 미션 |

- 숫자 · 날짜: 시간 "주 3시간", 비용 "월 3만 원"('만 원'은 띄어 씀), 범위 "10\~20만 원". 목록 날짜 10.15, 상세 2026.10.15, 알림 "3분 전"(7일이 넘으면 날짜).
- 버튼은 동사로 끝나는 2\~8자입니다(시작하기 · 등록 · 저장).
- 빈 상태 = 제목(무엇이 없는지) + 설명(다음에 할 수 있는 것) + 버튼(그 행동). 예: "아직 시작한 취미가 없어요" + "마음에 드는 취미를 찾아 첫 한 입을 시작해 보세요." + 취미 찾기 버튼.
- 오류 문구 예: "조건에 맞는 취미가 없어요. 조건을 하나씩 풀어 볼까요?" · "영상을 불러올 수 없어요. 다음 영상을 볼까요?" · "이메일 또는 비밀번호가 맞지 않아요." · "신고가 접수됐어요. 검토 후 알림으로 알려 드릴게요."(알림은 \[P2·MVP 제외\]라 도입 전에는 "검토 후 처리할게요")
- 음식 비유(냠냠 · 한 입 · 맛보기)는 캐릭터가 나오는 순간(빈 상태 · 완료 · 온보딩)에만 씁니다. 느낌표는 축하할 때 한 번만, 이모지와 영어 오류 코드는 화면에 쓰지 않습니다.

### 7.3 설계 규칙

- **비회원 데이터** \[P2·MVP 제외\]: `exploration_sessions`, `short_reactions`, `recommendations`는 `user_id` 대신 `guest_key`를 가질 수 있다. 이관 시 `user_id`를 채우고 `guest_key`를 비운다. 컬럼은 비회원 체험 도입에 대비해 남겨 두고, MVP에서는 항상 `user_id`를 채운다.
- **TODO 사본**: 시작하기 때 `plan_template_items` → `user_plan_items`로 행을 복사한다. 원본이 바뀌어도 사본은 그대로다(`template_version`으로 추적).
- **카운트 비정규화**: `like_count`, `comment_count`, `view_count`, `save_count`, `shorts.view_user_count`, `shorts.irrelevant_count`는 같은 트랜잭션에서 증감한다. 정합성이 어긋나면 야간 배치로 다시 센다.
- **숏폼 상태 흐름**: `NEEDS_REVIEW` →(관리자 승인) `CANDIDATE` →(주간 반영) `ACTIVE` → `UNAVAILABLE`(삭제·재생 불가) 또는 `AUTO_HIDDEN`(관련 없음 기준 초과). 필터 탈락·관리자 제외는 `REJECTED`. 사용자에게 보여 주는 쿼리는 항상 `status = 'ACTIVE'` 조건을 건다. 주간 반영은 `CANDIDATE`만 올리고, `NEEDS_REVIEW`는 관리자가 승인할 때까지 노출하지 않는다(승인하면 `CANDIDATE`가 되어 다음 반영에 포함, 거절하면 `REJECTED`). 검토 화면은 \[P3\]이지만 이 상태 구분은 P0 수집 배치에서 미리 저장한다.
- **콘텐츠 공개(MVP)**: 관리자 검토(FR-ADM-06)가 \[P2\]라 배치로 들어온 정보 피드·카카오 장소는 규칙·GPT 분류를 통과하면 `PENDING_REVIEW`를 거치지 않고 바로 `PUBLISHED`로 저장한다(스키마의 기본값은 그대로 두고 배치가 값을 지정). 취미·TODO 원본은 시드 SQL로 `PUBLISHED` 상태로 넣는다.
- **외부 데이터**: 수집 테이블(`shorts`, `youtube_channels`, `place_sources`, `feed_items`)은 출처 쪽 ID에 유니크 키를 걸어 배치를 다시 돌려도 중복이 생기지 않게 한다. 병합된 장소는 `places` 1행 + 출처별 `place_sources` n행이다.
- **삭제**: 사용자 콘텐츠는 `status = DELETED` 또는 `deleted_at`으로 soft delete. 탈퇴 회원은 `email`을 `withdrawn_{id}@deleted.local`, `nickname`을 `탈퇴한사용자{id}`로 바꾼다.
- **시간**: DB는 UTC, API 응답은 `+09:00` ISO 8601. 주차·"이번 주" 계산과 배치 시각은 Asia/Seoul 기준.

-- v0.4 메모(기능 요구사항 CSV 10/21 반영): 스키마는 바꾸지 않음. P2(MVP 제외) 기능용 테이블·컬럼
--       (guest_key, short_saves, interest_selections, notifications, feedbacks, PAUSED 등)은 고도화 대비로 남김
-- 규칙: 테이블·컬럼 snake_case / PK BIGINT IDENTITY / 시간 TIMESTAMP(6) UTC 저장 / TINYINT→SMALLINT(엔티티는 Short) / JSON→JSONB
--       enum은 VARCHAR + JPA @Enumerated(EnumType.STRING) / 삭제는 status 또는 deleted_at (soft delete)
-- 변환 메모: posts의 FULLTEXT(ngram) 인덱스는 PostgreSQL에 같은 기능이 없어 제외함.
--       게시글 검색 방식(pg_trgm, tsvector 등)을 정한 뒤 V2 마이그레이션으로 추가

-- ───────── 회원 ─────────
CREATE TABLE users (
  id                BIGINT       GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  email             VARCHAR(100) NOT NULL,
  password_hash     VARCHAR(100) NULL,
  nickname          VARCHAR(12)  NOT NULL,
  profile_image_url VARCHAR(500) NULL,
  role              VARCHAR(10)  NOT NULL DEFAULT 'USER',
  status            VARCHAR(10)  NOT NULL DEFAULT 'PENDING',
  email_verified_at TIMESTAMP(6)  NULL,
  interest_reset_at TIMESTAMP(6)  NULL,
  login_fail_count  INT          NOT NULL DEFAULT 0,
  locked_until      TIMESTAMP(6)  NULL,
  created_at        TIMESTAMP(6)  NOT NULL,
  updated_at        TIMESTAMP(6)  NOT NULL,
  withdrawn_at      TIMESTAMP(6)  NULL,
  CONSTRAINT uk_users_email UNIQUE (email),
  CONSTRAINT uk_users_nickname UNIQUE (nickname)
);
COMMENT ON COLUMN users.password_hash IS '소셜 전용 계정은 NULL';
COMMENT ON COLUMN users.role IS 'USER|ADMIN';
COMMENT ON COLUMN users.status IS 'PENDING|ACTIVE|WITHDRAWN';
COMMENT ON COLUMN users.interest_reset_at IS '관심사 초기화 시각. 이후 반응만 점수에 반영 (탐색 초기화는 P2)';

CREATE TABLE social_accounts (
  id               BIGINT       GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  user_id          BIGINT       NOT NULL,
  provider         VARCHAR(10)  NOT NULL,
  provider_user_id VARCHAR(100) NOT NULL,
  created_at       TIMESTAMP(6)  NOT NULL,
  CONSTRAINT uk_social UNIQUE (provider, provider_user_id),
  FOREIGN KEY (user_id) REFERENCES users (id)
);
COMMENT ON COLUMN social_accounts.provider IS 'GOOGLE (소셜 로그인은 Google만, P1)';

CREATE TABLE auth_tokens (
  id         BIGINT      GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  user_id    BIGINT      NOT NULL,
  type       VARCHAR(20) NOT NULL,
  token_hash CHAR(64)    NOT NULL,
  expires_at TIMESTAMP(6) NOT NULL,
  used_at    TIMESTAMP(6) NULL,
  created_at TIMESTAMP(6) NOT NULL,
  CONSTRAINT uk_token_hash UNIQUE (token_hash),
  FOREIGN KEY (user_id) REFERENCES users (id)
);
CREATE INDEX idx_token_user ON auth_tokens (user_id, type);
COMMENT ON COLUMN auth_tokens.type IS 'EMAIL_VERIFY(24h)|PASSWORD_RESET(30m)|REFRESH(14d)';
COMMENT ON COLUMN auth_tokens.token_hash IS 'SHA-256. 원문은 저장하지 않음';
COMMENT ON COLUMN auth_tokens.used_at IS '사용·폐기 시각';

CREATE TABLE regions (
  id      BIGINT      GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  code    VARCHAR(10) NOT NULL,
  sido    VARCHAR(20) NOT NULL,
  sigungu VARCHAR(30) NOT NULL,
  CONSTRAINT uk_region_code UNIQUE (code)
);
CREATE INDEX idx_region_sido ON regions (sido);
COMMENT ON COLUMN regions.code IS '행정구역 코드(시·군·구)';

CREATE TABLE user_conditions (
  user_id        BIGINT      NOT NULL PRIMARY KEY,
  weekly_hours   SMALLINT     NULL,
  monthly_budget INT         NULL,
  place_pref     VARCHAR(10) NULL,
  social_pref    VARCHAR(10) NULL,
  region_id      BIGINT      NULL,
  updated_at     TIMESTAMP(6) NOT NULL,
  FOREIGN KEY (user_id) REFERENCES users (id),
  FOREIGN KEY (region_id) REFERENCES regions (id)
);
COMMENT ON COLUMN user_conditions.weekly_hours IS '활동 가능 시간(시간/주) 0~40. NULL=미입력';
COMMENT ON COLUMN user_conditions.monthly_budget IS '예산(원/월). NULL=미입력';
COMMENT ON COLUMN user_conditions.place_pref IS 'INDOOR|OUTDOOR|ANY';
COMMENT ON COLUMN user_conditions.social_pref IS 'ALONE|TOGETHER|ANY';
COMMENT ON COLUMN user_conditions.region_id IS '선호 지역';

-- ───────── 취미 콘텐츠 ─────────
CREATE TABLE categories (
  id         BIGINT      GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  name       VARCHAR(30) NOT NULL,
  sort_order INT         NOT NULL DEFAULT 0,
  CONSTRAINT uk_category_name UNIQUE (name)

CREATE TABLE hobbies (
  id                  BIGINT       GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  category_id         BIGINT       NOT NULL,
  name                VARCHAR(30)  NOT NULL,
  summary             VARCHAR(100) NOT NULL,
  description         TEXT         NULL,
  place_type          VARCHAR(10)  NOT NULL,
  social_type         VARCHAR(10)  NOT NULL,
  difficulty          VARCHAR(10)  NOT NULL,
  session_min_minutes SMALLINT     NOT NULL,
  session_max_minutes SMALLINT     NOT NULL,
  initial_cost_min    INT          NOT NULL,
  initial_cost_max    INT          NOT NULL,
  monthly_cost_min    INT          NOT NULL,
  monthly_cost_max    INT          NOT NULL,
  supplies            TEXT         NULL,
  environment         TEXT         NULL,
  first_activity      TEXT         NULL,
  cautions            TEXT         NULL,
  thumbnail_url       VARCHAR(500) NULL,
  status              VARCHAR(10)  NOT NULL DEFAULT 'DRAFT',
  save_count          INT          NOT NULL DEFAULT 0,
  created_at          TIMESTAMP(6)  NOT NULL,
  updated_at          TIMESTAMP(6)  NOT NULL,
  CONSTRAINT uk_hobby_name UNIQUE (name),
  FOREIGN KEY (category_id) REFERENCES categories (id)
);
CREATE INDEX idx_hobby_category ON hobbies (category_id, status);
COMMENT ON COLUMN hobbies.place_type IS 'INDOOR|OUTDOOR|BOTH';
COMMENT ON COLUMN hobbies.social_type IS 'ALONE|TOGETHER|BOTH';
COMMENT ON COLUMN hobbies.difficulty IS 'EASY|NORMAL|HARD';
COMMENT ON COLUMN hobbies.session_min_minutes IS '1회 소요 시간(분) 최소';
COMMENT ON COLUMN hobbies.initial_cost_min IS '초기 비용(원)';
COMMENT ON COLUMN hobbies.monthly_cost_min IS '월 지속 비용(원)';
COMMENT ON COLUMN hobbies.supplies IS '준비물';
COMMENT ON COLUMN hobbies.environment IS '활동 환경 설명';
COMMENT ON COLUMN hobbies.first_activity IS '초보자용 첫 활동';
COMMENT ON COLUMN hobbies.cautions IS '유의 사항';
COMMENT ON COLUMN hobbies.status IS 'DRAFT|PUBLISHED|HIDDEN';
COMMENT ON COLUMN hobbies.save_count IS '관심 저장 수(인기순)';

CREATE TABLE tags (
  id   BIGINT      GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  name VARCHAR(20) NOT NULL,
  CONSTRAINT uk_tag_name UNIQUE (name)
);
COMMENT ON COLUMN tags.name IS '예: 실외, 활동적, 비용낮음';

CREATE TABLE hobby_tags (
  hobby_id BIGINT NOT NULL,
  tag_id   BIGINT NOT NULL,
  PRIMARY KEY (hobby_id, tag_id),
  FOREIGN KEY (hobby_id) REFERENCES hobbies (id),
  FOREIGN KEY (tag_id) REFERENCES tags (id)
);

CREATE TABLE hobby_similarity (
  hobby_id         BIGINT       NOT NULL,
  related_hobby_id BIGINT       NOT NULL,
  score            DECIMAL(5,4) NOT NULL,
  computed_at      TIMESTAMP(6)  NOT NULL,
  PRIMARY KEY (hobby_id, related_hobby_id),
  FOREIGN KEY (hobby_id) REFERENCES hobbies (id),
  FOREIGN KEY (related_hobby_id) REFERENCES hobbies (id)
);
COMMENT ON COLUMN hobby_similarity.score IS '0~1 코사인 유사도. Python 배치가 기록';

CREATE TABLE hobby_source_mappings (
  id         BIGINT      GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  hobby_id   BIGINT      NOT NULL,
  target     VARCHAR(20) NOT NULL,

COMMENT ON COLUMN hobby_source_mappings.target IS 'KAKAO_KEYWORD|PUBLIC_SPORTS|PUBLIC_PARK|EVENT_KEYWORD|SHORT_KEYWORD';

CREATE TABLE youtube_channels (
  id                  BIGINT       GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  youtube_channel_id  VARCHAR(30)  NOT NULL,

  hobby_id            BIGINT       NULL,
  status              VARCHAR(10)  NOT NULL DEFAULT 'CANDIDATE',

  hidden_short_count  INT          NOT NULL DEFAULT 0,

CREATE TABLE shorts (
  id                BIGINT       GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  hobby_id          BIGINT       NULL,
  channel_id        BIGINT       NULL,
  youtube_video_id  VARCHAR(20)  NOT NULL,
  title             VARCHAR(200) NOT NULL,
  description       TEXT         NULL,
  thumbnail_url     VARCHAR(500) NULL,
  duration_seconds  SMALLINT     NOT NULL,
  published_at      TIMESTAMP(6)  NULL,
  status            VARCHAR(12)  NOT NULL DEFAULT 'CANDIDATE',
  assign_method     VARCHAR(10)  NULL,
  assign_confidence DECIMAL(3,2) NULL,
  reject_reason     VARCHAR(20)  NULL,
  view_user_count   INT          NOT NULL DEFAULT 0,
  irrelevant_count  INT          NOT NULL DEFAULT 0,
  fail_user_count   INT          NOT NULL DEFAULT 0,
  released_at       TIMESTAMP(6)  NULL,
  last_checked_at   TIMESTAMP(6)  NULL,
  created_at        TIMESTAMP(6)  NOT NULL,
  updated_at        TIMESTAMP(6)  NOT NULL,
  CONSTRAINT uk_short_video UNIQUE (youtube_video_id),
  FOREIGN KEY (hobby_id) REFERENCES hobbies (id),
  FOREIGN KEY (channel_id) REFERENCES youtube_channels (id)
);
CREATE INDEX idx_short_hobby ON shorts (hobby_id, status);
CREATE INDEX idx_short_status ON shorts (status, created_at);
COMMENT ON COLUMN shorts.hobby_id IS '취미 지정 전·검토 대기면 NULL';
COMMENT ON COLUMN shorts.channel_id IS '수집한 신뢰 채널(시드 데이터는 NULL)';
COMMENT ON COLUMN shorts.duration_seconds IS '180 이하만 통과';
COMMENT ON COLUMN shorts.published_at IS 'YouTube 업로드 시각';
COMMENT ON COLUMN shorts.status IS 'CANDIDATE|NEEDS_REVIEW|ACTIVE|UNAVAILABLE|AUTO_HIDDEN|REJECTED';
COMMENT ON COLUMN shorts.assign_method IS 'CHANNEL|KEYWORD|GPT|ADMIN';
COMMENT ON COLUMN shorts.assign_confidence IS 'GPT 신뢰도 0~1';
COMMENT ON COLUMN shorts.reject_reason IS 'TOO_LONG|NOT_EMBEDDABLE|REGION_BLOCKED|NOT_PUBLIC|NOT_HOBBY|ADMIN';
COMMENT ON COLUMN shorts.view_user_count IS '고유 시청자 수(관련 없음 비율의 분모)';
COMMENT ON COLUMN shorts.irrelevant_count IS '관련 없음 고유 사용자 수';
COMMENT ON COLUMN shorts.fail_user_count IS '재생 실패를 보고한 고유 사용자 수. 3 이상이면 UNAVAILABLE';
COMMENT ON COLUMN shorts.released_at IS '주간 반영으로 ACTIVE가 된 시각';

COMMENT ON COLUMN shorts.created_at IS '수집 시각';

CREATE TABLE exploration_sessions (
  id           BIGINT      GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  user_id      BIGINT      NULL,
  guest_key    CHAR(36)    NULL,
  status       VARCHAR(12) NOT NULL DEFAULT 'IN_PROGRESS',
  max_count    SMALLINT     NOT NULL DEFAULT 12,
  viewed_count SMALLINT     NOT NULL DEFAULT 0,
  started_at   TIMESTAMP(6) NOT NULL,
  ended_at     TIMESTAMP(6) NULL,
  FOREIGN KEY (user_id) REFERENCES users (id)
);
CREATE INDEX idx_session_user ON exploration_sessions (user_id, started_at);
CREATE INDEX idx_session_guest ON exploration_sessions (guest_key);
COMMENT ON COLUMN exploration_sessions.guest_key IS '비회원 UUID. 이관 후 NULL (비회원 체험 P2, MVP는 항상 NULL)';
COMMENT ON COLUMN exploration_sessions.status IS 'IN_PROGRESS|COMPLETED|ABANDONED';

CREATE TABLE exploration_views (
  id          BIGINT      GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  session_id  BIGINT      NOT NULL,
  short_id    BIGINT      NOT NULL,
  seq         SMALLINT     NOT NULL,
  play_failed BOOLEAN     NOT NULL DEFAULT FALSE,
  watched_seconds SMALLINT NOT NULL DEFAULT 0,
  watch_ratio DECIMAL(4,3) NULL,
  viewed_at   TIMESTAMP(6) NOT NULL,
  CONSTRAINT uk_view UNIQUE (session_id, short_id),
  FOREIGN KEY (session_id) REFERENCES exploration_sessions (id),
  FOREIGN KEY (short_id) REFERENCES shorts (id)
);
COMMENT ON COLUMN exploration_views.seq IS '세션 내 노출 순서 1~N (N = exploration.session-size, 기본안 12)';
COMMENT ON COLUMN exploration_views.watched_seconds IS '실제 재생 초(영상 길이 상한)';
COMMENT ON COLUMN exploration_views.watch_ratio IS 'watched_seconds ÷ duration_seconds (0~1)';

CREATE TABLE short_reactions (
  id         BIGINT      GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  user_id    BIGINT      NULL,
  guest_key  CHAR(36)    NULL,
  short_id   BIGINT      NOT NULL,
  session_id BIGINT      NULL,
  type       VARCHAR(10) NOT NULL,
  created_at TIMESTAMP(6) NOT NULL,
  updated_at TIMESTAMP(6) NOT NULL,
  CONSTRAINT uk_reaction_user UNIQUE (user_id, short_id),
  CONSTRAINT uk_reaction_guest UNIQUE (guest_key, short_id),
  FOREIGN KEY (user_id) REFERENCES users (id),
  FOREIGN KEY (short_id) REFERENCES shorts (id)
);
CREATE INDEX idx_reaction_type ON short_reactions (user_id, type, updated_at);
COMMENT ON COLUMN short_reactions.session_id IS '반응한 탐색 세션(보관함(P2)에서 반응 시 NULL)';
COMMENT ON COLUMN short_reactions.type IS 'LIKE|DISLIKE|IRRELEVANT';

## 8. API 명세

REST API 약 90개를 아래 규칙으로 만듭니다. 여기는 **목록과 계약**만 정하고, 필드 단위 상세는 Swagger(springdoc, `/swagger-ui`)를 단일 기준으로 합니다.

### 8.1 공통 규칙

| 항목 | 규칙 |
| --- | --- |
| Base URL | `https://{api 도메인}/api/v1` (소셜 로그인 시작·콜백만 `/oauth2/**`, `/login/oauth2/**`) |
| 인증 | `Authorization: Bearer {accessToken}`. Refresh는 `refresh_token` 쿠키(HttpOnly, Path=`/api/v1/auth`) |
| 비회원 식별 | \[P2·MVP 제외\] `guest_key` 쿠키(HttpOnly, 7일). 서버가 첫 비회원 탐색 때 발급(비회원 체험 도입 시) |
| 형식 | JSON UTF-8, 필드 camelCase, enum UPPER\_SNAKE, 일시 ISO 8601 `2026-10-16T16:30:00+09:00`, 날짜 `2026-10-16`, 금액 원(정수), 시간 분(정수) |
| 페이지 | `?page=0&size=20` (0부터, size 최대 50). 응답은 `content` + `page` |
| HTTP 상태 | 200 조회·수정, 201 생성, 202 접수(비동기), 204 삭제, 400/401/403/404/409/413/422/429, 500/503 |
| 요청 추적 | 모든 응답에 `X-Request-Id` 헤더. 오류 제보·로그 검색에 씁니다 |
| 요청량 제한 | 5.1 정책. 응답 헤더 `X-RateLimit-Remaining`, 초과 시 `429` + `Retry-After` |
| CORS | 프론트 도메인(Vercel 배포 주소, `localhost:5173`)만 허용, `credentials: true` |

모든 응답은 같은 봉투를 씁니다. 목록은 `data` 안에 `content`와 `page`가 들어갑니다.

```json
{
  "success": false,
  "data": null,
  "error": {
    "code": "COMMON_INVALID_INPUT",
    "message": "입력값을 확인해 주세요.",
    "fields": [{ "field": "nickname", "reason": "2~12자로 입력해 주세요." }],
    "retryAfterSeconds": null
  }
}
```

```json
{
  "success": true,
  "data": {
    "content": [{ "postId": 120, "title": "클라이밍 입문 한 달 후기" }],
    "page": { "number": 0, "size": 20, "totalElements": 134, "totalPages": 7, "hasNext": true }
  },
  "error": null
}
```

### 8.2 엔드포인트 목록

권한: **공개** 누구나 · **체험** 비회원(guestKey)·회원 · **회원** 로그인 필수 · **본인** 소유자만 · **관리자** ADMIN. 경로는 Base URL 뒤에 붙습니다. 비회원 체험이 \[P2·MVP 제외\]라 MVP에서 **체험**은 **회원**과 같게(로그인 필수) 동작합니다.

**우선순위 표시** 기능 칸 뒤의 `[P1]` `[P3]` `[P2]`는 그 엔드포인트의 우선순위(4.0 정의)이고, 표시가 없으면 P0입니다. `[P2]`는 MVP에서 만들지 않습니다.

| `UPLOAD_TOO_LARGE` | 413 | 파일 크기 초과 |
| `ADMIN_NOT_PUBLISHABLE` | 422 | 필수 항목 누락으로 공개 불가(`fields`) \[P2\] |
| `COMMON_RATE_LIMITED` | 429 | 요청량 초과(`retryAfterSeconds`) |
| `COMMON_INTERNAL` | 500 | 서버 오류 |
| `COMMON_EXTERNAL_UNAVAILABLE` | 503 | 외부 API 장애로 대체 응답도 불가 |

## 9. 시스템 구성 및 기술 스택

프론트는 Vercel, API·배치·메시지 큐·Redis·DB는 EC2 한 대의 Docker 컨테이너(Docker Compose)로 운영하고, 백엔드 배포는 같은 서버의 Jenkins가 맡습니다. 외부 API(GMS, YouTube Data, 카카오 로컬, 공공·문화 데이터, 메일)는 모두 백엔드를 거치고, 프론트가 직접 부르는 것은 YouTube 플레이어와 지도 SDK뿐입니다.

### 9.5 환경·배포

- **환경** `local`(`BE/docker-compose.yml`로 PostgreSQL·Redis·RabbitMQ 실행) · `dev` · `prod`. 비밀값은 서버 `.env`와 Jenkins Credentials에만 둔다. OAuth 키는 Google만 발급하고(Kakao·Naver OAuth 키는 두지 않음), 카카오 앱 키는 지도·로컬 API 용도로만 둔다.
- **브랜치** `master`(운영) ← `dev`(통합·기본 브랜치, 보호) ← `feature/{JIRA키}-{설명}`. `dev`에는 직접 푸시하지 않고 MR로만 병합하며, MR은 1명 이상 승인 후 병합. MR 설명에 `Closes {JIRA키}`를 적으면 병합 시 Jira 이슈가 완료된다.
- **배포** 백엔드는 `dev`에 `BE/` 변경이 병합되면 GitLab 웹훅 → Jenkins(`BE/Jenkinsfile`)가 테스트(임시 PostgreSQL로 `./gradlew test`, 실패 시 배포 중단) → Docker 이미지 빌드(`BE/Dockerfile`) → EC2 `/home/ubuntu/app`에서 `docker compose up -d --force-recreate backend` → `/actuator/health` 확인(실패 시 이전 이미지로 롤백) → Mattermost 알림. 프론트는 Vercel이 `main`을 자동 배포하고, MR마다 미리보기 URL을 만든다.
- **도메인** 프론트는 Vercel 배포 주소, API는 `https://k15d104.p.ssafy.io/api`(Nginx가 `/api/`를 백엔드 컨테이너 `127.0.0.1:18080`으로 전달, `/actuator`는 외부에 열지 않음). 프론트와 API의 도메인이 달라 Refresh 쿠키 속성(SameSite·Secure)은 따로 확인한다.
