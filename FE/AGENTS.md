# FE Development Guidelines

이 문서는 `FE` 저장소에서 작업하는 개발자와 코딩 에이전트가 따라야 하는 기본 규칙이다.
사용자의 현재 요청이 이 문서와 충돌하면 사용자 요청을 우선하되, 충돌 사실과 영향을 먼저 알린다.

## 1. 기준과 우선순위

### API 기준

- 프런트엔드의 엔드포인트, HTTP 메서드, 요청·응답 필드, Enum, 인증 방식, 에러 코드는 백엔드 API 명세를 기준으로 작성한다.
- 현재 기준 문서는 `C:\Users\SSAFY\Desktop\자율(be, ai)\S15P31D104\repo\docs\spec\api-spec.md`이다.
- 런타임 Swagger가 제공되고 문서와 다르면 차이를 보고한 뒤 어느 쪽을 따를지 확인한다. 임의로 한쪽을 선택해 계약을 바꾸지 않는다.
- 명세에 없는 엔드포인트는 정식 계약으로 간주하지 않는다. 필요한 경우 `experimental` 또는 개발용 어댑터로 격리하고 그 사실을 코드에 드러낸다.
- 프런트 편의를 위해 요청·응답 필드명이나 Enum 값을 임의로 변경하지 않는다.

### 디자인 기준

- 화면은 디자인 북과 정의된 디자인 컴포넌트를 기준으로 구현한다.
- 디자인 북과 Figma 컴포넌트가 충돌하면 최신 업데이트인 Figma 컴포넌트를 우선한다.
- Figma에서 확인되지 않은 크기, 간격, 색상, 상태는 디자인 토큰과 기존 컴포넌트 관례를 우선하고 임의의 새 규칙을 만들지 않는다.
- 다른 프로젝트에서 가져온 `FRONTEND_STRUCTURE.md`, `agents.md` 등의 자료는 형식 참고용일 뿐, 현재 프로젝트의 구현 기준으로 복사하지 않는다.

## 3. 기본 기술 구성

프로젝트 설정이 생기면 실제 `package.json`, 빌드 설정, 팀 합의를 우선한다. 새 구성을 시작할 때의 기본 선택은 다음과 같다.

- React + TypeScript
- 서버 상태: TanStack Query
- 전역 클라이언트 상태: 필요한 경우에만 Zustand
- 폼과 검증: React Hook Form + Zod
- 단위·컴포넌트 테스트: Vitest + React Testing Library
- API 모킹: MSW

라이브러리를 설치하기 전에 기존 의존성으로 해결할 수 있는지 확인한다. 비슷한 역할의 라이브러리를 중복 도입하지 않는다.

## 4. 파일 확장자 기준

- `.tsx`: JSX를 포함하는 React 컴포넌트, 페이지, 레이아웃, Provider
- `.ts`: JSX가 없는 타입, API 함수, Query 옵션, 스키마, 상태 저장소, 유틸리티, 상수
- `.css`: 전역 스타일과 디자인 토큰. CSS Modules를 채택한 경우 컴포넌트 전용 스타일은 `.module.css`
- `.test.ts` / `.test.tsx`: 테스트 대상의 JSX 사용 여부에 맞춘 테스트
- `.stories.tsx`: Storybook이 실제로 도입된 경우에만 작성
- `.d.ts`: 외부 모듈이나 전역 타입 보강이 반드시 필요한 경우에만 사용

JSX가 없는 파일을 습관적으로 `.tsx`로 만들지 않는다. 새 `.js`·`.jsx` 파일은 만들지 않고 TypeScript를 사용한다.

## 5. 권장 소스 구조

실제 초기 설정 또는 팀 구조가 정해지면 그것을 우선한다. 별도 기준이 없을 때는 다음 책임 경계를 사용한다.

```text
src/
  app/          # 앱 진입점, Router, 전역 Provider
  pages/        # 라우트 단위 화면 조합
  features/     # 사용자 기능 단위 UI, hook, model
  entities/     # 핵심 도메인 모델과 재사용 가능한 도메인 UI
  shared/
    api/        # 공통 API client, 인증, 에러 정규화
    ui/         # 디자인 시스템 기반 공통 컴포넌트
    hooks/      # 도메인 비종속 공통 hook
    lib/        # 순수 유틸리티
    styles/     # 전역 스타일과 디자인 토큰
    types/      # 여러 기능에서 공유하는 타입
  mocks/        # MSW handler와 fixture
```

- 페이지는 라우팅과 화면 조합을 담당하고, 재사용 가능한 로직과 UI를 페이지 파일에 누적하지 않는다.
- 동일 기능에만 쓰이는 코드는 해당 `feature` 가까이에 둔다.
- `shared`는 두 곳 이상에서 실제로 재사용되거나 도메인에 종속되지 않은 코드만 둔다.
- 의미 없는 `common`, `utils`, `components` 거대 폴더를 만들지 않는다.
- 순환 의존성을 만들지 않으며, 하위 계층이 페이지나 앱 계층을 import하지 않게 한다.

## 6. API 연동 규칙

- 실제 API를 연결하거나 교체할 때 기본 데이터 흐름은 `API DTO → adapter → feature hook → page/component`로 둔다.
- `page/component`는 API DTO를 직접 해석하거나 서버 필드명에 맞춰 렌더링하지 않고, 화면에 필요한 view model을 props 또는 feature hook으로 받는다.
- adapter는 서버 DTO를 화면 모델로 변환하며, 날짜·시간 표시, nullable 기본값, Enum 라벨, 중첩 필드 평탄화를 담당한다.
- feature hook은 Query/Mutation, 로딩·오류 상태, 캐시 갱신과 사용자 동작을 담당하고 DOM 구조나 CSS 클래스명을 결정하지 않는다.
- API 연결만 요청된 작업에서는 기존 JSX 구조, CSS 클래스명, 디자인 토큰, 문구, 에셋과 레이아웃을 변경하지 않는다. 화면 변경이 불가피하면 먼저 변경 이유와 영향을 보고한다.
- 서버 응답 타입은 API 명세에서 파생해 작성한다. 화면에 필요한 모델이 다르면 API DTO를 변경하지 말고 명시적인 변환 함수를 둔다.
- 서버 상태는 TanStack Query로 관리한다. API 응답을 Zustand에 중복 저장하지 않는다.
- Query Key는 기능별 factory로 관리해 문자열을 화면 곳곳에 직접 작성하지 않는다.
- GET 조회는 Query, 서버 상태를 변경하는 요청은 Mutation으로 구분한다.
- 인증이 필요한 API는 공통 API client에서 Access Token 헤더와 공통 에러 처리를 적용한다.
- Refresh Token은 HttpOnly 쿠키를 전제로 하며 JavaScript에서 직접 읽거나 저장하지 않는다.
- 서버 Enum과 식별자는 문자열 가공으로 추측하지 말고 명세의 값을 그대로 사용한다.
- 사용자에게 표시할 한국어 라벨은 서버 Enum과 분리된 매핑으로 관리한다.
- 공통 응답 봉투의 `success`, `data`, `error` 구조를 고려한다. HTTP 성공 여부만 보고 비즈니스 성공으로 판단하지 않는다.
- 오류 화면은 최소한 인증 만료, 권한 부족, 입력 오류, 찾을 수 없음, 충돌, 서버 오류를 구분할 수 있게 한다.

## 7. API 미연결 상태의 UI 구현

- API가 확정되거나 구현되기 전에도 HTML/JSX와 스타일 구현을 진행할 수 있다.
- 화면 컴포넌트가 직접 임시 배열이나 `fetch`에 강하게 결합되지 않게 한다.
- 페이지 데이터는 props, feature hook 또는 별도 adapter를 통해 주입한다.
- 개발용 데이터는 실제 API 응답 형태를 따르는 typed fixture로 만들고 `mocks`에 둔다.
- API가 연결되면 fixture를 Query hook으로 교체할 수 있도록 화면과 데이터 접근을 분리한다.
- 기본 화면만 만들지 말고 해당 페이지에 필요한 로딩, 빈 결과, 오류, 정상, 비활성 상태를 함께 구현한다.
- 개발용 API나 임시 응답을 사용하면 정식 API와 혼동되지 않도록 이름과 위치에서 구분한다.

## 8. 컴포넌트와 스타일

- Figma에 정의된 공통 컴포넌트가 있으면 새로 만들지 않고 재사용한다.
- 버튼, 입력, 모달, 카드처럼 반복되는 UI는 디자인 시스템 컴포넌트로 구현한다.
- 페이지별 컴포넌트에서 색상, 폰트, 간격 값을 반복해서 하드코딩하지 않는다. 디자인 토큰을 사용한다.
- 컴포넌트 props는 화면 문구보다 역할과 상태를 표현하도록 설계한다.
- boolean props가 늘어나 상태 조합이 모호해지면 `variant` 또는 명시적인 상태 타입을 사용한다.
- 컴포넌트 내부에서 라우팅, API 호출, 전역 상태를 불필요하게 결합하지 않는다.
- 접근성을 기본 요건으로 본다. 시맨틱 HTML, 키보드 조작, label 연결, 포커스 표시, 이미지 대체 텍스트를 확인한다.
- 모바일과 데스크톱 기준이 존재하면 두 화면을 모두 확인하며, 근거 없이 임의의 breakpoint를 늘리지 않는다.

## 9. 상태와 폼

- 서버에서 가져온 데이터는 TanStack Query에 둔다.
- 입력 중인 폼 상태는 React Hook Form 또는 컴포넌트 지역 상태에 둔다.
- 여러 화면에서 지속되어야 하는 순수 클라이언트 상태만 Zustand를 검토한다.
- URL로 표현할 수 있는 검색어, 필터, 페이지 번호는 가능한 한 URL 상태로 관리한다.
- API 명세의 필수값, 길이, 형식, Enum 제약을 Zod 스키마에 반영한다.
- 클라이언트 검증은 사용자 피드백을 위한 것이며 서버 검증을 대체하지 않는다.

## 10. TypeScript와 코드 작성

- `any` 사용을 피한다. 외부 입력은 `unknown`으로 받고 검증 후 좁힌다.
- API DTO, 화면 모델, 폼 값을 서로 다른 책임으로 보고 필요할 때 타입을 분리한다.
- 타입 단언(`as`)으로 오류를 숨기지 않는다.
- 공개 함수와 컴포넌트의 이름은 역할이 드러나게 작성한다.
- 과도한 추상화보다 작은 순수 함수와 명확한 데이터 흐름을 선호한다.
- 주석은 코드가 무엇을 하는지 반복하지 말고, 명세 제약이나 선택 이유처럼 코드만으로 알기 어려운 내용을 설명한다.
- 기존 formatter와 linter 설정이 생기면 그 설정을 따른다. 개인 스타일로 대규모 포맷 변경을 만들지 않는다.

## 11. 테스트 기준

- 사용자가 보는 동작을 중심으로 테스트한다. 내부 구현 세부사항이나 CSS 클래스명에 의존하지 않는다.
- 중요 페이지는 정상 데이터뿐 아니라 로딩, 빈 결과, 오류 상태를 확인한다.
- 폼은 필수값, 경계값, 서버 오류 표시를 확인한다.
- API 연동 테스트는 MSW로 실제 계약 형태를 모킹한다.
- 버그를 수정할 때는 재현 가능한 경우 회귀 테스트를 추가한다.
- 스냅샷 테스트만으로 핵심 동작을 검증하지 않는다.

## 12. 작업 전후 확인

작업 전:

1. 관련 Figma 컴포넌트와 디자인 북을 확인한다.
2. 관련 API 명세와 현재 BE 구현을 읽고 차이를 확인한다.
3. 기존 컴포넌트, hook, 타입, Query Key가 있는지 검색한다.
4. BE·AI·공통 문서를 수정하지 않는 범위인지 확인한다.

작업 후:

1. TypeScript 검사, lint, 관련 테스트를 실행한다.
2. 로딩·빈 결과·오류·정상 상태를 확인한다.
3. Figma와 다른 부분이 없는지 확인한다.
4. API 필드, Enum, 인증, 응답 봉투가 명세와 일치하는지 확인한다.
5. 새 의존성, 임시 API, 남은 불확실성이 있으면 결과에 명시한다.

## 13. 금지 사항

- BE, AI, 공통 문서 코드를 허가 없이 수정하지 않는다.
- 명세에 없는 API 필드나 Enum을 추측해 정식 코드에 넣지 않는다.
- 임시 mock을 운영 API처럼 숨기지 않는다.
- 서버 데이터를 Zustand와 TanStack Query에 중복 보관하지 않는다.
- Refresh Token이나 민감한 값을 `localStorage`에 저장하지 않는다.
- 디자인 토큰이 있는데 임의 색상과 간격을 반복해서 하드코딩하지 않는다.
- 다른 프로젝트의 구조나 가이드 파일을 현재 프로젝트에 그대로 복제하지 않는다.
- 요청 범위와 무관한 리팩터링이나 전체 파일 포맷 변경을 함께 수행하지 않는다.
